## Z80 review notes (read, nothing found beyond the above)
Stack discipline in the new `link_request` loop (balanced push/pop, `di`/`ei` pairs around the `v_evflags` read), per-task scratch (`v_tmp*` are swapped on context switch, the new variable `v_lnkabort` is a plain kernel variable `VARS+$3F`, free before), `link_direct` clears the abort flag before running in the caller's context.
Possible race kept as is: if CLEAR is already held when `link_request` starts, the request is cancelled at once (harmless: the caller shows the "no answer" message). **Wrong - see pass 2, finding C3: it broke leaving a streamed game.**

## Hardware risks (cannot be reduced without the calculator)
1. **Signature/boot code**: the `.8xu` is signed with key `04` by `rabbitsign`. Since pass 2 `tools/verify_8xu.py` also recomputes the RSA check (sig^17 mod n == MD5 of header + pages); it was claimed impossible before, and the old modulus was read byte-reversed. What remains untested is a real boot code accepting it (revision differences).
2. **Page $7C**: the OS image contains page `$7C` (the flash-unlock stub the settings journal and DIAGNOSTICS need). Whether page `$7C` is inside the area the boot code lets an OS upgrade overwrite on your revision is an assumption made from documentation. If the upgrade is rejected or the unit does not boot, resend a TI OS (see `HARDWARE_TEST.md`).
3. **Hardware revision / geometry**: RAM page numbering, flash sector size, the LCD controller timing (`lcd_cmd` delay) and the contrast range were taken from documentation and Tilem's emulation, not from your unit.
4. **Turbo link, ESP32 bit-banging, Peanut-GB speed, CAS timings, Wi-Fi services, power draw**: unmeasured (need the ESP32 / instruments).

## Minor (noted, not changed unless said)
* `selftest_noesp`: the "request ends with a message" check is unconditionally true for `OTA PC packages` (exempted by name); `failed_shown` is computed and unused.
* `link_direct` does not check `F_LINK`: if the ESP32 ever sends an unsolicited frame between two streamed frames, the link task and the game loop would drive the port together. The current firmware never initiates traffic, so it cannot happen today; guard it if notifications are added.
* After CLEAR cancels a chat, the ESP32 keeps waiting for DeepSeek (up to 150 s) without reading the link: every request in that window fails with "no answer". Stale replies are not mistaken for a new answer (they arrive as unsolicited frames and are dropped). Needs a cancel command in the protocol.
* A CAS task that never ends keeps `cas_running` set until reboot (by design: the engine has global state).
* `secret_seal` IVs come from `esp_random()` before the radio is on (pseudo-random per the IDF docs); with CTR this matters only together with the obfuscation caveat above.
* `tools/build.py` does not check `mktiupgrade`'s exit code (a stale intermediate would be signed); `verify_8xu.py` catches it by comparing with the dev ROM.
* The upload body deadline is 15 s + 1 s per 20 KB: a 1.5 MB Game Boy ROM may hold the main loop ~90 s (user-initiated).
* The `$A5` at `$0057` is stamped by `rabbitsign -r`, not by `mktiupgrade` (comments corrected).
* The throw-away test ROMs of `c8test.py` / `mathtest.py` reuse the dev boot stub; they start at `$0000`, so their scripts point the stub there (the first full run after the `$0053` change failed 0/20 in `c8test` for that reason, which is what the change was meant to expose).
* Not tested: the I3 backstop after a *transient* error with the chip awake (a wake pulse into an awake chip, no ESP_READY, `v_esp` kept). The Python model of the ESP32 has no per-byte time-outs (the firmware has them), so in the emulator a stray pulse would desynchronise the model rather than the code under test.
* DQ5 vs. the poll counter: the tests prove that a failed program/erase ends (no hang); they cannot tell whether the DQ5 branch or the counter ended it (Tilem raises DQ5, the counter is the backstop).
* `selftest_review` 25b/25e add the virtual-ESP32 knob `HZ_ESP_REPLY_DELAY_MS`; the Python model still does not implement job timeouts, sealed NVS or the upload server.

## Decisions of pass 1, reviewed
* **Key poll interval kept at 28 ms: agree.** The 37 ms trial gained 0.3 points of HALT (96.7 -> 97.0 %, launcher idle), far below anything a battery test could resolve, and lost real 50 ms taps. 28 ms keeps at least one sample inside a 50 ms tap.
* **No 6 MHz while idle: agree.** HALT already dominates idle (~97 %), and every link timeout and the turbo layer are counted in CPU loops (`SL_TMO`, `TL_*`): a clock change while the link task can run would silently change protocol timing. Worth doing only after a current measurement on the real unit shows that 6 MHz + HALT is meaningfully lower than 15 MHz + HALT.

## Hardware risks after pass 2 (re-assessed)
1. Signature acceptance by your boot code revision: the math is verified, acceptance is untested.
2. Page `$7C` in the upgrade (privileged page with the flash-unlock stub): assumed writable by the boot code during an upgrade; untested here. If the boot code refuses it, the upgrade fails and the TI OS goes back with the DEL procedure.
3. Boot hand-off (`$0053` and `$0000` both lead to `boot` now), LCD pacing, RAM page numbering, flash sector geometry: from documentation and Tilem, not from your unit.
4. Flash programming with DQ5 / time-outs follows the JEDEC/AMD behaviour as Tilem emulates it; the real chip's timing is untested.
5. ESP32: everything changed in passes 1 and 2 is compiled only.

## Found on the real unit (TI-83 Plus SE, boot code 1.00, OS 1.19)
* **C-HW1 (critical, fixed): the OS was signed with key `0104` (the APP key); the OS key is `04`.** The boot code rejected every build at the end of the transfer (the calculator showed `ERROR! Press any key to turn unit off`; its progress bar stops at pages_sent/14 because it measures against a full TI OS). Evidence: `sig^17 mod n == MD5(header + pages)` holds for key `04` on the official TI OS 1.19 and on KnightOS (which boots on this unit), and for key `0104` only on our old files. `build.py` and `verify_8xu.py` now use `tools/keys/04.key`. The emulator and the old verifier could not catch it: they never check *which* key. Not yet confirmed on the unit with the new signature.
* **C-HW2 (critical, fixed, unconfirmed on the unit): signature record layout.** `rabbitsign` writes the 67-byte signature as 3 x 32-byte records at addresses 0000/0020/0040 padded with FF; TI's OS and KnightOS write 32 + 32 + 3 bytes, all at address 0000, then `:00000001FF   -- CONVERT 2.6 --`. The signature value is identical (re-signing KnightOS' data with `04.key` reproduces it), so only the layout differs. `tools/fix_8xu_tail.py` (called by `build.py`) rewrites it; re-signing KnightOS with our chain + this fix gives a file byte-identical to the original except 4 header bytes. `verify_8xu.py` checks the layout.

* **C-HW3 (critical, fixed, unconfirmed on the unit): the LCD was initialised from the emulator's model.** Disassembling KnightOS and the official TI OS 1.19 (`tools/z80dis.py trace FILE.8xu 0053`) shows: the LCD init sequence is `05 01 03 17 0B` then the contrast (`17` / `0B` = power and bias, missing here); the LCD command is `C0 + 24 + (0..39 setting)`, so our profile bases of 24/26/34 were a contrast of 0-10 (blank on a real panel; KnightOS sends 52 = `F4`) - bases are now 48/50/58; KnightOS sets the execution-protection ports `25=0 26=FF 22=FF 23=FF` before `out (20),1` and the interrupt mask. The boot now draws a progress bar of 9 stages with its own stackless LCD code (`crumb_ns`) and `dist/SuperOS_bringup.8xu` adds a 0-63 contrast sweep. Symptom that led here: installs fine, 'a flash and nothing' on the screen.

## Found on the real unit, round 2 (after the first boot): keyboard, games, tools
Reports from the TI-83+SE: "the keyboard does not work well", "Snake crashes after a few seconds and restarts", "the Invaders do not move", "the Pong enemy is too slow and never reaches the ball".

* **C-HW4 (critical, fixed, unconfirmed on the unit): keyboard settle time.** The official OS waits about 40 T-states between selecting a matrix row and reading it at 15 MHz (disassembled: `out`, 3 NOP, `JR`, 4 NOP); every scan here waited 16-24 T. Keys were read before the matrix settled (missed or ghost keys; a "wait for any key" restart in Snake fired immediately). All scans now wait 12 NOPs (48 T). Snake "crashes" were deaths by walls with unsteerable keys, not resets.
* **C-HW5 (important, fixed): CHIP-8 interpreter showed half-drawn frames.** The 150-instruction burst per tick can stop in the middle of a frame (Invaders erases and redraws 15 aliens: more than 150 opcodes); the picture was shown anyway, so aliens and the ship blinked in and out. A frame is now shown only when the game reached its `Fx07` wait (or after 4 ticks). Side effect: CHIP-8 games went from ~70 % to ~92 % HALT.
* **I-HW1 (fixed): CHIP-8 Pong AI** followed the ball one step in two (half the ball's vertical speed): it could not reach it. Now three steps in four.
* **I-HW2 (fixed): CHIP-8 games never put the calculator to sleep** (the key scan did not watch the idle timer). They do now.
* **Tooling**: `tools/check_labels.py` (spasm accepts a label and an `.equ` with the same name; the second one silently wins and a `JR Z` jumped into RAM: found while writing the native games), `tools/audit_text.py` (24-column limit on every UI string), `tools/z80dis.py` (disassembler and boot tracer), crash trail (the ISR records the PC and SP every tick; after an unexpected restart the next boot prints them: `REINICIO PC=.... SP=....`), DIAGNOSTICS 7 TIMING (tick rate against the crystal RTC, CPU speed), `hz80_sim`'s `softreset` event.
* **Native games**: seven games on a shared library (`glib.z80`: frame pacing, matrix scan, LFSR, rectangles, sprites, numbers, overlays, high scores, **tile flush**: only the 8x8 tiles that changed are sent to the LCD, with a paused-picture check that the LCD equals the frame buffer). Measured HALT %: Breakout waiting 49 -> 94, Pong playing 66 -> 88, Invaders 48 -> 61 (full-screen redraw per frame; see `docs/PERF.md`).
* **Emulator note**: `get_lcd()` of the Tilem core lags about three frames behind the LCD memory for moving objects (same with full blits), so LCD-versus-buffer comparisons are only valid for static pictures.
